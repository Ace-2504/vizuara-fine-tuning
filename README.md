# SLM Fine-Tuning & Evaluation Backend

The fine-tuning, evaluation, and serving backend for a family of small language
models — **125M**, **500M**, and **Gemma-2-2b** — for US legal / financial / general-web
question answering. It turns three base models into instruction-following,
retrieval-augmented, and preference-aligned variants, evaluates them under a common
rubric, and serves them behind a single API for the demo frontends and arenas.

One shared codebase covers all three model families; a base model is selected by a
`--model` / config switch rather than duplicated per model.

---

## What's here

The pipeline takes each base model through four alignment stages, plus the data
build, evaluation harness, and serving layer that surround them.

**Data build** — teacher-distilled supervised data from the pretraining corpus:
grounded question–answer pairs (**QA-SFT**) and a retrieval-augmented variant with
distractor contexts and abstention targets (**RAFT**). See `build.py`, `chunker.py`,
`prompts.py`, `teacher.py`, and `DATASET-BUILD-GUIDE.md`.

**Fine-tuning stages** — hand-rolled trainers (no training-framework version risk),
run on Modal GPUs (L4 for the small models, A100 for Gemma; QLoRA adapters for Gemma,
full fine-tuning for 125M/500M):

| Stage | Script | What it does |
| --- | --- | --- |
| **QA-SFT** | `finetune/train_{125m,500m,gemma}.py --method sft` | Supervised fine-tuning on grounded Q&A |
| **RAFT** | `finetune/train_{125m,500m,gemma}.py --method raft` | Retrieval-augmented fine-tuning (distractors + abstention) |
| **DPO** | `finetune/train_dpo.py` | Direct preference optimization over a preference set |
| **RLAIF** | `finetune/train_reward.py` → `finetune/train_ppo.py` | Reward model + PPO against AI feedback |

Each model family has a step-by-step guide: `FINETUNE-125M-GUIDE.md`,
`FINETUNE-500M-GUIDE.md`, `FINETUNE-GEMMA-2B-GUIDE.md`.

**Evaluation** — a blind, rubric-based LLM-judge harness plus reference-based metrics
(token-F1, a fabrication check), scored over held-out clean and adversarial
conditions. See `evaluations/` and `EVAL-HARNESS-REVIEW.md`.

**Serving** — a FastAPI server that hosts every model behind one endpoint
(load-on-demand, shared Gemma backbone + LoRA adapters), with `/generate` and a
`/judge` route used by the eval harness and the arena frontends. See
`finetune/serve_api.py` and `finetune/serve_local.py`.

## Repository layout

| Path | What it is |
| --- | --- |
| `finetune/` | Trainers (`train_*`), model/data config (`ft_config.py`, `ft_data.py`), and the serving API |
| `build.py`, `chunker.py`, `prompts.py`, `teacher.py` | Supervised-data build (teacher distillation, chunking, prompts) |
| `evaluations/` | Eval harness, judge, and analysis scripts |
| `cards/` | Model cards for each fine-tuned variant (SFT / RAFT / DPO / RLAIF) |
| `bugs/` | Post-mortems for issues hit during the runs |
| `cost-audit/` | Cost-reconciliation tooling |
| `*-GUIDE.md` | Per-model fine-tuning guides and the dataset-build guide |

Large artifacts — the corpus, checkpoints, generated datasets, and local secrets —
are gitignored and regenerated by the pipeline; a fresh clone re-fetches source data
rather than storing gigabytes in git.

## Running it

Python 3.12. Training and evaluation run on [Modal](https://modal.com) GPUs and
require a Modal account and a Hugging Face token (for the gated Gemma base).

```bash
pip install -r requirements.txt

# fine-tune a stage (examples)
modal run finetune/train_125m.py --method sft      # QA-SFT
modal run finetune/train_gemma.py --method raft    # RAFT (QLoRA)
modal run finetune/train_dpo.py --model 500m       # DPO
modal run finetune/train_reward.py                 # reward model, then:
modal run finetune/train_ppo.py --model 125m       # RLAIF (PPO)

# serve every model locally for the frontends
python finetune/serve_api.py                       # FastAPI on :8000
```
